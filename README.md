# Billing Dashboard

Дашборд команды Billing по Stripe и Solidgate: конверсия триальных подписок в платные и оборот. Данные берутся напрямую из API провайдеров, складываются в локальную SQLite и обновляются каждые 4 часа.

**Что считаем** (метрики с примерами — [VPN](public/methodology-vpn.md) и [eSIM](public/methodology-esim.md), откуда данные — [public/data-sources.md](public/data-sources.md); все три открываются в дашборде по кнопке «Methodology»; решения — в [спеке](docs/specs/2026-10-12-trial-conversion-dashboard-design.md)):
- **Когорта** — триалы, оформленные в день D по времени провайдера, как в его кабинете: Stripe — `TIMEZONE` (по умолчанию America/New_York — как в Stripe и Campaignswell), Solidgate — `SOLIDGATE_TIMEZONE` (по умолчанию UTC — как в Solidgate Hub), начиная с `HISTORY_FROM`. Отменённые во время триала входят в знаменатель.
- **Сконвертилось** — первый платный инвойс оплачен в течение `RETRY_WINDOW_DAYS` (30) дней после конца триала, с любой попытки.
- **Из них с первой попытки** — оплачен первой автоматической попыткой.
- Пока по дню ещё идут триалы или ретраи, цифра растёт: в таблице это «≈», на графике — пунктир.
- **Проходимость / decline** — по попыткам списания первого платного периода (включая ретраи): успешные (отклонённые) попытки / все попытки.
- **Рефанды** — доля сконвертившихся, кому вернули первый платёж.
- **Разрезы:** аккаунт (Stripe Corp / Org / … и каналы Solidgate), страна карты, способ оплаты (Apple Pay / Google Pay / карта), банк-эмитент (только Solidgate — Stripe его не отдаёт), платёжная система, причины отказа (коды Stripe и Solidgate сведены к общим названиям). Фильтры по всем разрезам собираются в панели «Filters» слева (например, Solidgate + США + Google Pay + конкретный MID); в одном фильтре можно отметить несколько значений — они складываются, разные фильтры сужают выборку; клик по строке разреза — тоже фильтр и динамика по этому значению; активные фильтры — чипами над карточками. Таблицы сортируются кликом по заголовку колонки.
- **Оборот** (экран «Volume») — все успешные списания по дню платежа в USD: оборот, рефанды, оборот без рефандов, платежи, средний чек; доля в обороте по MID (Stripe — аккаунт, Solidgate — MID заказа), стране, способу оплаты, банку и платёжной системе. Платежи Solidgate не в USD пересчитываются по дневному курсу.
- **eSIM** (переключатель VPN / eSIM, если задан `ESIM_STRIPE_KEY`) — свой Stripe-аккаунт без подписок. **Overview** — по дням: выручка, оплаченные заказы, новые клиенты и повторные заказы, доля оплаченных заказов (без отсечённых антифродом), потерянная выручка, причины неоплаты; разрезы по направлению, пакету, стране и способу оплаты. **Retention** — когорты по первой покупке: вернулись за 30 дней, выручка на клиента за 90 дней.
- **Язык:** интерфейс на английском, названия метрик и причин отказа — общепринятые (как в Stripe); при наведении на название — короткое пояснение по-русски.
- **Темы:** светлая и тёмная — переключатель внизу панели «Filters», выбор хранится в браузере; без выбора — как в системе.
- **Вход:** страница входа, две роли. Админ (`ADMIN_USER` / `ADMIN_PASSWORD`) видит всё и запускает синк; гость (`GUEST_USER` / `GUEST_PASSWORD`, необязательно) только смотрит. Старые `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` работают как вход админа. Сессия — 30 дней; смена любого логина или пароля разлогинивает всех.

**Источники:** Stripe (любые аккаунты из `STRIPE_KEYS`) и Solidgate Reports API (каналы из `SOLIDGATE_KEYS`).

## Ключи

- **Stripe:** в каждом нужном аккаунте (Toggle Org, Toggle Corp, …) создать restricted key с правами **Read** на Subscriptions, Customers, Payment Methods, Invoices, Charges, Refunds и Events.
- **Solidgate:** public и secret key мерчантов `sg` и `sgH2H` с доступом к Reports API.

Ключи вписываются в `.env`, файл не коммитится.

## Локальный запуск

Нужен Node ≥ 22.13 (используется встроенный `node:sqlite`).

```bash
cp .env.example .env   # вписать ключи и логины/пароли ADMIN_* и GUEST_*
npm install
npm run dev            # http://localhost:3000, вход — ADMIN_* или GUEST_*
```

При первом запуске сервер сам начинает догрузку истории с `HISTORY_FROM`:
- прогресс виден в логе;
- прерывать безопасно — после перезапуска продолжит с того же дня;
- Solidgate `sgH2H` с 1 сентября — около минуты; Stripe Corp — подписки ~20 минут, инвойсы и списания (попытки оплаты, ~15 тыс. в сутки) — ещё около получаса.

База, выгруженная до появления оборота, при следующем синке один раз заново проходит списания Stripe и заказы Solidgate с `HISTORY_FROM` — чтобы сохранить платежи. Это порядка 10–15 минут на неделю истории по всем аккаунтам Stripe (с 1 сентября — около полутора часов), потом синк снова идёт секунды.

Сдвинуть `HISTORY_FROM` **раньше** можно без удаления базы: при следующем синке каждый аккаунт догрузит только недостающее начало истории — подписки этих дней, а инвойсы и списания ещё на 7 дней триала и 30 дней ретраев вперёд, чтобы у последних триалов куска были оплаты и попытки (проход списаний заодно сохраняет оборот). Уже загруженное остаётся на месте, догрузка продолжается с того же дня после перезапуска. Сдвинуть позже — данные до новой даты просто не показываются. Если убрал аккаунт или хочешь начать с нуля — останови сервер и удали папку `data/`.

Дальше синк идёт по `SYNC_CRON` (по умолчанию каждые 4 часа), по кнопке «Refresh» (только админ) и при старте сервера, если последний успешный синк был больше суток назад. Синк забирает только новое — секунды по каждому аккаунту.

Другие команды:

```bash
npm run sync        # разовый синк без сервера, в конце — таблица статусов
npm run digest      # сводка для Slack по локальной базе — напечатать; с -- --send ещё и отправить
npm test            # vitest
npm run typecheck
```

## Сводка в Slack

Каждый день в 06:00 UTC поток синка делает свежий синк и отправляет в Slack сводку за вчера:
- новые триалы;
- первые платежи у последних окончательных когорт;
- отмены;
- VAMP по мерчантам.

Триалы, платежи и отмены — итогом и по аккаунтам, рядом Δ к среднему за 7 дней. Как считается каждая цифра — в методологии VPN, раздел «Сводка в Slack».

Включить:
1. В Slack: **Apps → Incoming Webhooks → Add to Slack**, выбрать канал, скопировать адрес вебхука.
2. На хостинге задать `SLACK_WEBHOOK_URL` — это секрет: не коммитить и не пересылать в чатах. Без него сводки нет.
3. Необязательно: `DASHBOARD_URL` — ссылка на дашборд внизу сводки.

Повторов и пропусков не будет:
- в базе отмечается день отправки, второй раз в те же сутки сводка не уйдёт;
- если сервис перезапустился после 06:00, сводка за сегодня уйдёт при старте;
- если Slack недоступен, сервис сделает 3 попытки с паузой в минуту, потом запишет ошибку в журнал. Сводка уйдёт при следующем старте в те же сутки.

`npm run digest` собирает сводку по локальной базе без синка. Флаг `--send` отправляет её по `SLACK_WEBHOOK_URL` из `.env`, например в тестовый канал. Плановую отправку это не затрагивает.

## Посмотреть базу

Файл `data/dashboard.sqlite` (SQLite) можно открыть в DBeaver или `sqlite3 -readonly`. Время хранится в unix-секундах (`trial_started_at`, `paid_at`, …), а рядом есть вычисляемые колонки с обычной датой по UTC — `trial_started_utc`, `trial_ended_utc`, `paid_utc`, `attempted_utc`, `started_utc`/`finished_utc` у синков, `value_utc` у курсоров. Они не занимают места и считаются при чтении. В строке триала лежат и итоги его попыток (`attempts`, `approved`, `refunded`) и `mid` — так метрики считаются одним проходом по `trials`; посчитанные ответы сервер держит в памяти до следующего синка. Сутки в дашборде режутся по часовому поясу провайдера (Stripe — Нью-Йорк, Solidgate — UTC).

## Деплой

Подойдёт любой хостинг контейнеров с постоянным диском:
- volume под `/app/data` — там лежит `dashboard.sqlite`;
- переменные окружения — как в `.env.example`;
- health check — `GET /health` (без авторизации);
- без входа открыты только `/health`, страница входа и `public/assets` (стили, иконка); остальное — после входа (API принимает и заголовок Basic — для скриптов).

Запускать одну реплику: синк и база живут в одном процессе. Синк идёт в отдельном потоке (`src/sync-worker.ts`) со своим соединением с базой: запросы SQLite синхронные, и в одном потоке с сервером запись и пересчёты на десятки секунд останавливали ответы — Render не получал ответа на `/health` за 5 с и перезапускал сервис (502). Сервер только читает, поток пишет; база в режиме WAL, они не мешают друг другу.
