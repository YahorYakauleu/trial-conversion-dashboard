# Trial → Paid dashboard — дизайн

Дата: 2026-10-12 · Автор: Yahor Yakauleu · Статус: утверждён

## 1. Цель

Регулярно обновляемый дашборд для команды Billing, который показывает конверсию триальных подписок в платные отдельно для Stripe и Solidgate и в сумме.

В workflow-service эту метрику посчитать нельзя: у подписки хранится только текущий статус (`trial` перезаписывается на `active`), дат триала нет, транзакции привязаны к аккаунту, а не к подписке. Поэтому дашборд — отдельный проект, который берёт данные напрямую из API провайдеров.

## 2. Скоуп

**Входит в v1**
- Две метрики («с первой попытки» и «с учётом ретраев») по дню окончания триала.
- Разрез только по провайдеру: Все / Stripe / Solidgate. Stripe — сумма по всем аккаунтам, ключи которых заданы в конфиге.
- История за 90 дней, автоматический синк раз в сутки и ручной синк по кнопке.
- Локальный запуск на localhost и Dockerfile для последующего деплоя на хостинг.

**Не входит в v1**
- Разрезы по стране, плану, способу оплаты, источнику трафика.
- Вычет рефандов и чарджбэков.
- Учёт продления или досрочного окончания триала после первой выгрузки подписки.
- Уведомления в Slack, сверка с Campaignswell, изменения в workflow-service.
- Пользователи и роли — только один общий basic auth.

## 3. Определения метрики

Все даты в UTC.

- **Единица** — подписка с триалом (не пользователь).
- **Когорта D** — все триалы, у которых `trial_ended_at` попадает в UTC-день D. Триал, который ещё не закончился (`trial_ended_at > now`), в метрики не входит. Триалы, отменённые во время пробного периода, входят в знаменатель как несконвертившиеся.
- **Первый платный инвойс** — первый инвойс подписки за период после окончания триала с суммой > 0. Платёж за платный триал (например, $0.99) конверсией не считается.
- **ended(D)** — число триалов в когорте D.
- **paid_first(D)** — число триалов, у которых первый платный инвойс оплачен с первой попытки списания.
- **paid_retry(D)** — число триалов, у которых первый платный инвойс оплачен в течение `RETRY_WINDOW_DAYS` (по умолчанию **30**) после `trial_ended_at`, с любой попытки.
- **rate_first = paid_first / ended**, **rate_retry = paid_retry / ended**. Для «Все» числитель и знаменатель суммируются по провайдерам; проценты не усредняются.
- **Окончательность цифры:**
  - rate_first окончательна, когда D + 2 дня ≤ сегодня (первая попытка проходит в течение суток после конца триала);
  - rate_retry окончательна, когда D + `RETRY_WINDOW_DAYS` + 1 ≤ сегодня (последний триал дня D заканчивается в 23:59, и ему тоже нужно полное окно).
- **Неделя** — ISO-неделя (с понедельника, UTC). Цифра за неделю окончательна, когда окончательны все её дни. Первая неполная неделя в начале истории не показывается, чтобы не занижать `ended`.

## 4. Архитектура

Node 24 + TypeScript, один процесс, фронт без сборки.

| Компонент | Выбор |
|---|---|
| HTTP | Express |
| Хранилище | SQLite через встроенный `node:sqlite` (Node ≥ 22.13), один файл в `DATA_DIR`; нативных зависимостей нет |
| Расписание | `node-cron`, внутри процесса |
| Stripe | официальный SDK `stripe`, `maxNetworkRetries: 3` |
| Solidgate | `fetch` + подпись запросов так же, как в `workflow-service/src/common/providers/payment/solidgate/solidgate.service.ts` |
| Фронт | `public/index.html` + Chart.js с CDN |
| Тесты | vitest |
| Запуск TS | `tsx` (dev), `tsc` → `node dist` (prod) |

### Контракт TrialRow

Единственное, что провайдеры отдают наружу. `metrics.ts` и UI не знают, откуда пришла строка.

| поле | тип | смысл |
|---|---|---|
| `provider` | `'stripe' \| 'solidgate'` | |
| `account` | string | `org`, `corp`, … для Stripe; `sg`, `sgH2H` для Solidgate |
| `subscription_id` | string | id подписки у провайдера |
| `trial_started_at` | unix-секунды (UTC) | |
| `trial_ended_at` | unix-секунды (UTC) | плановый конец триала на момент выгрузки |
| `first_invoice_id` | string \| null | первый платный инвойс, если уже создан |
| `first_attempt_succeeded` | boolean \| null | `null`, пока первой попытки не было (или она ещё в процессе) |
| `paid_at` | unix-секунды \| null | когда первый платный инвойс оплачен |

### Схема SQLite

- `trials` — колонки TrialRow + `synced_at`; первичный ключ `(provider, subscription_id)`; индекс по `trial_ended_at`. При upsert поля оплаты сливаются через `COALESCE`: повторная выгрузка без данных об оплате не стирает уже известные. `first_attempt_succeeded = false` необратимо: события приходят в любом порядке.
- `sync_runs` — `id, provider, account, kind ('backfill'|'daily'), started_at, finished_at, status ('running'|'ok'|'error'), error, items`.
- `sync_state` — `(provider, account, key) → value`: курсор ежедневного синка и прогресс бэкфилла (последний обработанный день).

Email, имена и данные карт не хранятся.

## 5. Сбор данных

Первый запуск при пустой `trials` делает бэкфилл, потом синк идёт раз в сутки по `SYNC_CRON` (по умолчанию `0 5 * * *`, UTC) и по кнопке. Бэкфилл идёт кусками по дню и сохраняет прогресс в `sync_state`, поэтому после прерывания продолжается с того же места.

### Stripe (на каждый аккаунт из `STRIPE_KEYS`)

Ключ — restricted, read-only: Subscriptions, Invoices, Events. SDK `stripe@18` с API `2025-08-27.basil`, как в workflow-service. В basil id подписки у инвойса лежит в `parent.subscription_details.subscription`; события могут прийти в старой версии API, поэтому читаем и `invoice.subscription`.

**Бэкфилл**
1. `GET /v1/subscriptions?status=all&created[gte]&created[lt]` по дням за `HISTORY_DAYS + TRIAL_LOOKBACK_DAYS` (по умолчанию 90 + 31). Берём только подписки с непустыми `trial_start` и `trial_end`. Строки с `trial_end` в будущем тоже сохраняем: это триалы, которые ещё идут.
2. `GET /v1/invoices?created[gte]&created[lt]` по дням за `HISTORY_DAYS + 1`. Оставляем `billing_reason = subscription_cycle` и `amount_due > 0`, подписка должна быть в `trials`. Для каждой подписки берём самый ранний такой инвойс с `created ≥ trial_end − 1 час`. Фильтровать по `period_start` нельзя: у инвойса `subscription_cycle` поля `period_start`/`period_end` относятся к предыдущему периоду, то есть к триалу.
3. Из инвойса:
   - `first_attempt_succeeded` = `status == 'paid' && attempt_count == 1 && paid_at − finalized_at ≤ 1 час`. Если `attempt_count == 0` — `null`, иначе `false`. Проверка времени нужна, потому что ручная оплата после отказа не увеличивает `attempt_count`. На живых данных Toggle Org (99 инвойсов продления) все оплаты с первой попытки укладываются в час после финализации.
   - `paid_at` = `status_transitions.paid_at`.

**Ежедневно**
1. Новые подписки: `created ≥ курсор − 1 день` (перекрытие на случай задержек).
2. События `GET /v1/events?types[]=invoice.paid&types[]=invoice.payment_failed&created[gte]=курсор − 1 день`. Из объекта инвойса в событии по тем же правилам обновляем `first_invoice_id`, `first_attempt_succeeded` и `paid_at`. Инвойс из события принимается как первый платный, только если `first_invoice_id` ещё пуст или совпадает с ним. Так следующий месячный инвойс не перетрёт первый. Stripe хранит события 30 дней, этого хватает для ежедневного синка с запасом.

Считаем только подписки Stripe Billing, а не отдельные списания. Поэтому платежи Solidgate, которые идут через Stripe-аккаунт «Toggle Org (Solidgate copy)», не задвоятся.

Ожидаемый объём: порядка 6k новых кастомеров в день у Toggle Org, Sigma не включена. Бэкфилл — десятки минут, ежедневный синк — минуты.

### Solidgate

Мерчантов несколько, как в workflow-service: `sg` (платёжная форма) и `sgH2H` (wallet, host-to-host). Для каждого — live public и secret key с доступом к Reports API.

**Бэкфилл и ежедневно**
1. Reports API v1: `POST https://reports.solidgate.com/api/v1/subscriptions` с `filter: updated_at`, пагинация через `next_page_iterator`, подпись как в workflow-service. Отчёт отдаёт подписку вместе с `invoices` → `orders` (`status`, `retry_attempt`, `processed_at`). Окна по 1 дню: бэкфилл — за `HISTORY_DAYS + TRIAL_LOOKBACK_DAYS`, ежедневно — с `курсор − 1 день`.
2. Берём подписки с триалом: `product.trial = true` и `product.trial_period > 0` (минуты). `trial_started_at = started_at`, `trial_ended_at = started_at + trial_period`. Единицы и смысл полей подтверждаются на живых данных скриптом разведки до написания нормализатора.
3. Первый платный инвойс — первый инвойс с `billing_period_started_at ≥ trial_ended_at` и `amount > 0`.
   - `first_attempt_succeeded` — самая ранняя попытка оплаты (order) этого инвойса успешна.
   - `paid_at` — время первой успешной попытки оплаты этого инвойса.

**Источник деталей инвойса.** По документации отчёт уже содержит инвойсы и попытки оплаты. Если на живых данных их нет — для подписок, у которых `trial_ended_at` попадает в окно `[сегодня − HISTORY_DAYS, сегодня]` и `paid_at` ещё пуст, детали берём через `POST /subscription/status` (ответ содержит `invoices` с `orders`). Объёмы Solidgate пока небольшие, поэтому это приемлемо.

## 6. HTTP API и UI

| Роут | Auth | Ответ |
|---|---|---|
| `GET /` | basic | `public/index.html` |
| `GET /api/metrics?provider=all\|stripe\|solidgate&granularity=day\|week` | basic | `{ generated_at, retry_window_days, cards, series[], sync[] }` |
| `POST /api/sync` | basic | `202` — синк запущен; `409` — уже идёт |
| `GET /health` | нет | `200 ok` |

`series[]`: `period, ended, paid_first, paid_retry, rate_first, rate_retry, final_first, final_retry`.
`sync[]`: `provider, account, last_success_at, last_status, last_error`.

**Страница**
- **Шапка:** «Trial → Paid», время последнего обновления, статус синка по каждому провайдеру (галочка или красная отметка с текстом ошибки), кнопка «Обновить». Пока синк идёт, на кнопке написано «идёт синк».
- **Переключатели:** провайдер (Все / Stripe / Solidgate) и шаг (день / неделя).
- **Карточки:**
  1. «Триалов закончилось, 7 дн» — сумма `ended` за последние 7 полных дней (D ∈ [сегодня − 7, сегодня − 1]);
  2. «С первой попытки, 7 дн» — `paid_first / ended` за последние 7 полных дней, у которых rate_first окончательна;
  3. «С ретраями, дозревшие 7 дн» — `paid_retry / ended` за последние 7 дней, у которых rate_retry окончательна.
- **График:** столбики `ended` на правой оси; линии `rate_first` (зелёная) и `rate_retry` (фиолетовая) на левой оси в %. Участок, где rate_retry ещё не окончательна, — пунктиром.
- **Таблица:** период, ended, paid_first (шт и %), paid_retry (шт и %), окончательна ли цифра.

## 7. Ошибки

- Провайдеры и аккаунты синкаются независимо. Ошибка одного пишется в `sync_runs` и не трогает данные остальных. Последние успешные данные остаются на странице, ошибка видна в шапке.
- Повторные попытки при ошибках API: у Stripe встроены в SDK; у Solidgate — до 3 повторов с экспоненциальной паузой на 429 и 5xx.
- Upsert по `(provider, subscription_id)` — повторный запуск синка безопасен.
- Одновременно идёт только один синк (lock внутри процесса). Если процесс упал во время синка, запись в `sync_runs` со статусом `running` при старте помечается `error`.
- Записи провайдера, которые не удалось разобрать, пропускаются; их число пишется в лог и в `sync_runs.error`.

## 8. Тесты

- **Нормализация** на фикстурах Stripe и Solidgate:
  - триал отменён во время пробного периода;
  - оплачен с первой попытки;
  - оплачен на ретрае внутри окна;
  - оплачен после окна;
  - не оплачен;
  - платный триал;
  - первой попытки ещё не было.
- **Метрики** на SQLite в памяти:
  - флаги окончательности цифры;
  - группировка по дням и неделям;
  - границы суток UTC;
  - сумма для «Все»;
  - карточки.
- Тестов против живых API нет. После первого запуска сверить 1–2 дня вручную с Stripe Dashboard и Solidgate Hub.

## 10. Риски

| риск | что делаем |
|---|---|
| Реальный ответ Reports API расходится с документацией (нет `invoices`/`orders`, другие единицы `trial_period`) | скрипт разведки до нормализатора; запасной путь через `/subscription/status` (раздел 5) |
| Нет доступа к Reports API у текущих ключей | запросить доступ в Solidgate Hub до начала работ над `providers/solidgate.ts`; Stripe-часть от этого не зависит |
| Бэкфилл Stripe упирается в rate limit | запросы идут последовательно, SDK повторяет при 429, прогресс бэкфилла сохраняется по дням |
| Триал продлили или завершили досрочно | v1 берёт `trial_end` на момент выгрузки подписки (ограничение зафиксировано в скоупе) |
| Двойные триалы у одного человека (дабл-сабмит) | считаются как две подписки — так задумано, единица метрики — подписка |
